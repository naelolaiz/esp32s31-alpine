# 2026-10-07: Alpine riscv32 boots in QEMU (step 10)

Phase 3, in the sibling `alpine-riscv32` repository: the guide is its
`docs/steps/10-qemu-system.md`.

## Kernel

Mainline Linux 6.18, tarball checked against kernel.org's `sha256sums.asc`,
built in the container with the step 8 cross compiler:

```sh
make ARCH=riscv CROSS_COMPILE=riscv32-alpine-linux-musl- rv32_defconfig
make ARCH=riscv CROSS_COMPILE=riscv32-alpine-linux-musl- -j$(nproc) Image
```

- `rv32_defconfig` is riscv's `defconfig` plus `32-bit.config`. It already
  has the virtio disk, network and 9p, ext4, the 8250 serial console and
  devtmpfs, so no options were changed.
- `arch/riscv/boot/Image` is 31,021,568 bytes, uncompressed. The board's own
  xipImage is about 3.8 MB; this is a generic config, not a small one.
- The kernel compiles C without F/D and assembles its FPU save/restore with
  `fd`, so the soft-float toolchain builds it unchanged.

## Running riscv32 programs on the PC: binfmt_misc

apk runs each package's install scripts inside the new root, and they are
riscv32 programs. busybox's script creates every applet link, `/sbin/init`
included, so without the scripts nothing boots. The host had no binfmt
handlers.

- Alpine's `qemu-riscv32` is statically linked and ships the rule in
  `/usr/lib/binfmt.d/qemu-riscv32.conf`.
- The binary was copied out of the container, and the rule registered on the
  host pointing at the copy, with flags `PF`.
- `F` makes the kernel open the interpreter at registration time, so the rule
  also works inside the container and in chroots.
- The magic is the first 20 bytes of a 32-bit little-endian ELF header with
  machine 0xf3 (RISC-V).
- Test: `chroot <tree> /bin/busybox uname -m` prints `riscv32` with no qemu
  in the command.
- The registration is gone after a reboot of the PC.

## Root file system

As container root:

1. `apk add --root <tree> --initdb --arch riscv32 alpine-base` from the local
   repository: 25 packages, 7696 KiB. apk chroots into the tree to run each
   script, and binfmt runs them.
2. One harmless warning: `failed to create initial device nodes: Operation
   not permitted`. apk tries to `mknod` `/dev/null` and similar in the tree,
   which a rootless container may not do; the kernel mounts devtmpfs over
   `/dev` at boot anyway.
3. Settings:
   - the `ttyS0` getty enabled in `inittab` (it ships commented out);
   - `/dev/vda` in `fstab`;
   - the host name;
   - `rc-update add` for devfs, dmesg and mdev (sysinit), hostname, bootmisc,
     sysctl and syslog (boot), killprocs and mount-ro (shutdown).
4. `mkfs.ext4 -d <tree> ... 256M` builds the image straight from the
   directory, owners included, without mounting anything.

## Boot

```sh
qemu-system-riscv32 -M virt -m 256M -nographic \
	-kernel /work/linux-6.18/arch/riscv/boot/Image \
	-append "root=/dev/vda rw console=ttyS0" \
	-drive file=/work/qemu/alpine-rv32.img,format=raw,if=virtio
```

QEMU's default firmware on `virt` is OpenSBI, so the sequence is the board's
minus U-Boot: OpenSBI, then Linux in supervisor mode.

```
Welcome to Alpine Linux 3.25.0_alpha20260805 (edge)
Kernel 6.18.0 on riscv32 (/dev/ttyS0)

alpine-rv32 login: root
alpine-rv32:~# uname -a
Linux alpine-rv32 6.18.0 #1 SMP Wed Oct  7 02:47:58 UTC 2026 riscv32 Linux
```

- `rc-status -a`: every enabled service started. OpenRC also pulled in
  modules, hwclock, sysfs, fsck, root and localmount as dependencies.
- hwclock starts. It runs through the busybox hwclock patch from step 9, and
  QEMU's virt board has an RTC.
- `free` right after login: 228,656 KiB total, 9,080 KiB used. Used counts the
  kernel's runtime allocations and all of userspace, not the kernel image.

## apk inside the VM

The local repository is shared read-only with
`-virtfs local,path=/work/.local/share/abuild,mount_tag=repo,security_model=none,readonly=on`
and mounted in the VM with `mount -t 9p -o trans=virtio,version=9p2000.L repo /mnt`.

`apk add --repository /mnt/main file` installed file and libmagic 5.48, with
the signature checked against the local key, and grew the system to 18.0 MiB
in 27 packages. Most of the growth is libmagic's compiled magic database.
`file /bin/busybox` inside the VM: `ELF 32-bit LSB pie executable, UCB RISC-V,
RVC, soft-float ABI ... interpreter /lib/ld-musl-riscv32-sf.so.1`.

## What it means for the board

- The userspace is ready: the same packages should run on the ESP32-S31 once
  its kernel can mount an ext4 root from the pendrive (steps 12 and 13).
- A minimal Alpine root is about 7.5 MiB on disk. 9 MB used after login on a
  generic kernel is a first hint for a board with about 12 MB free; the real
  number comes from the board's own kernel.
