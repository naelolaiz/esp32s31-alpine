# 2026-10-10: What Linux needs to run on both harts (SMP study)

The ESP32-S31 has two RV32 cores (harts), and Linux uses only hart 0. This
entry reads Espressif's sources and GrieferPig's port, which runs Linux on
both harts, and lists what each layer of the boot chain needs for SMP
(symmetric multiprocessing: one kernel scheduling work on both harts). The
board steps are in [`docs/steps/smp.md`](../steps/smp.md).

Sources read on 2026-10-10:

| Source | Commit | What it has for hart 1 |
| --- | --- | --- |
| [espressif/opensbi](https://github.com/espressif/opensbi) `integration/v1.6-esp32s31` | 5395e03 (merge of 2026-10-06) | starts and stops hart 1 |
| [espressif/u-boot](https://github.com/espressif/u-boot) `integration/v2024.07-esp32s31` | b2ec9ae (merge of 2026-10-06) | `cpu@1` in U-Boot's device tree |
| [espressif/linux](https://github.com/espressif/linux) `integration/v6.18-esp32s31` | dc0e382 (unchanged, our kernel) | nothing |
| [GrieferPig/linux-esp32-s31](https://github.com/GrieferPig/linux-esp32-s31) `v6.18-esp32-s31` | 52dc6ea4 | working SMP, his README says "stable" |
| [GrieferPig/opensbi-esp32-s31](https://github.com/GrieferPig/opensbi-esp32-s31) `v1.9-esp32-s31` | 344cfcb | his own hart 1 start, timers and idle code |

In short:

- Espressif has done the boot stack half. On 2026-10-06 its OpenSBI gained
  the code that starts hart 1 and its U-Boot device tree gained `cpu@1`.
  Our board runs the versions from just before those merges.
- Espressif's kernel has no SMP code at all. Turning `CONFIG_SMP` on and
  adding `cpu@1` to the kernel's device tree starts hart 1, but hart 1 then
  gets no timer, no inter-processor interrupts (IPIs) and a wrong view of
  the interrupt controller. GrieferPig had to write all of that.
- Nothing here conflicts with the Wi-Fi plan, provided OpenSBI and U-Boot
  are updated together (the SRAM section explains why).
- SMP does not open a new hole for the SIGILL problem, but it makes that
  problem harder to study, so it should be understood on one hart first.

## How a second hart starts

On RISC-V, Linux does not start a hart itself. It asks the M-mode firmware
through the SBI HSM extension (Hart State Management): `hart_start(hartid,
start_addr, opaque)`. On this chip that goes:

1. Linux on hart 0 calls `hart_start(1, secondary_start_sbi, ...)`
   (`arch/riscv/kernel/cpu_ops_sbi.c:65`).
2. OpenSBI's platform code releases hart 1: it clears the hart's software
   stall in `PMU_CPU_STALL_SW_REG`, turns on its clocks and takes it out of
   reset in `HP_SYS_CLKRST_HPCORE1_CTRL0`, and tells the ROM where to jump
   with the ROM function `ets_set_cpu_boot_addr` (Espressif's `hsm.c`).
3. Hart 1 runs the ROM, which jumps to OpenSBI's warm boot entry in SRAM.
4. OpenSBI sets hart 1 up like hart 0: the PSRAM PMA entry
   (`s31_pma_init`, which runs on every hart), its PMP regions, and its own
   bank of the CLIC interrupt controller. Then it drops to S-mode at
   `secondary_start_sbi`.
5. Linux on hart 1 runs `smp_callin()`: it registers the hart's timer,
   enables its IPIs and marks it online.

From then on each hart needs its own timer interrupt (the scheduler tick),
a way to interrupt the other hart (IPIs, for "reschedule", "run this
function" and TLB flushes), and interrupt controller settings that reach
the right hart.

## The boot stack: what Espressif merged on 2026-10-06

OpenSBI, branch `feat/esp32s31_smp`, merged as 5395e03:

| Commit | Change |
| --- | --- |
| 77d2190 | `hsm.c`: an HSM device named `esp32s31-hsm` that starts and stops hart 1 (step 2 above). Stopping puts hart 1 back in reset. |
| 9b77505 | The CLIC set-up moves from "boot hart only" to a per-hart `warm_init`, so hart 1's CLIC bank also hands sources 16 to 47 to S-mode. |
| 9edf48f | Fixes where the `nmbits` field sits in the CLIC's `cliccfg` register (bits 5:4, not 6:5). This runs on hart 0 too. |

U-Boot, merged as b2ec9ae, adds one commit, 7dee42f: `cpu@1` in U-Boot's
device tree and `heap-size = <0x7000>` for OpenSBI. U-Boot SPL hands this
device tree to OpenSBI, and OpenSBI learns how many harts exist from it.
Without `cpu@1` there, the new OpenSBI still refuses to start hart 1.

Our board: the step 19 `grep` found `esp32s31-reset` but not
`esp32s31-hsm` in `u-boot.itb`, so our OpenSBI is 6597eea, the branch head
before the merge. The merges are dated 2026-10-06 18:35 UTC and our build
2026-10-06 19:19 UTC, so U-Boot is most likely d8d3bbe, also from before
its merge (inferred; the guide checks it).

U-Boot SPL already turns on hart 1's instruction cache and its bus to
flash (`cache_enable_all()` in `board/espressif/esp32s31/spl_cache_mmu.c`,
`CACHE_L1_ICACHE_SHUT_IBUS1` cleared in `spl_flash.c`), so hart 1 can
execute the kernel in place from flash. GrieferPig does the same in his
OpenSBI (`smp.c`), which shows it is needed.

What Espressif's OpenSBI still does not have: an IPI device and a timer
device. Its `platform/generic/configs/esp32s31_defconfig` leaves
`CONFIG_FDT_IPI` and `CONFIG_FDT_TIMER` off, and the platform code
registers neither. So:

- An SBI IPI or SBI remote fence to hart 1 fails: `sbi_ipi_raw_send()`
  returns `SBI_EINVAL` when there is no IPI device (`lib/sbi/sbi_ipi.c:259`).
  Starting hart 1 does not need IPIs, because the HSM device releases the
  hart directly.
- An SBI timer request does nothing. Hart 0 does not care, because Linux
  uses the chip's systimer through its own driver.

## SRAM: OpenSBI with two harts

OpenSBI sits at 0x2F000000. Behind its code and data it places, at run
time, one 8 KiB stack per hart and a heap (`firmware/fw_base.S`,
`_scratch_init`). It then fences off its RW part from S-mode with a PMP
region, which must be a power of two in size and aligned to it
(`sbi_domain_memregion_init()`). The RW part starts at 0x2F020000, so it
gets 64 KiB and ends at 0x2F030000 as long as it stays below that, and
128 KiB, up to 0x2F040000, as soon as it does not.

From the step 19 `readelf` (data and BSS end at 0x2F023B88, so `_fw_end`
is 0x2F024000 after page alignment) and the default heap
`0x8000 + 0x1000 × harts`, plus 32 bytes per hart² for TLB requests,
rounded up to 1 KiB (`platform/generic/platform.c:63`):

| OpenSBI | Harts | Stacks | Heap | End | PMP fence ends at |
| --- | --- | --- | --- | --- | --- |
| ours today | 1 | 8 KiB | 37 KiB (default) | 0x2F02F400 | 0x2F030000 |
| Espressif SMP, with U-Boot's heap cap | 2 | 16 KiB | 28 KiB (`heap-size = <0x7000>`) | 0x2F02F000 | 0x2F030000 |
| Espressif SMP, without the cap | 2 | 16 KiB | 41 KiB (default) | 0x2F032400 | **0x2F040000** |

This assumes the new code and data end at the same page as today; the
guide reads it from the new build. The third row is why Espressif capped
the heap ("reduces the memory available for uboot proper and Linux (for
DMA descriptors)", 7dee42f): a fence up to 0x2F040000 would cover the DMA
pool today and the radio's SRAM after step 20. OpenSBI and U-Boot have to
be updated together.

These numbers refine the step 19 estimate (about 0x2F02E000) with the
formula OpenSBI uses.

## The kernel: Espressif's has no SMP code

Espressif's `esp32s31_minimal_defconfig` has no `CONFIG_SMP`, and its
drivers assume one hart. With only `CONFIG_SMP=y` and `cpu@1` in the
kernel's device tree, this is what would go wrong, from reading the code
(none of it tested on the board yet):

1. **Hart 0 loses its tick.** The systimer clockevent claims
   `cpu_possible_mask` (`timer-esp32s31-systimer.c:176`). With two possible
   CPUs, `tick_check_percpu()` (`kernel/time/tick-common.c:272`) accepts a
   device that covers more than one CPU only if its interrupt affinity can
   be set, and the interrupt matrix driver has no `irq_set_affinity`. So
   hart 0 would tick from the RISC-V timer instead, whose counter, by
   Espressif's own comment in the same file, stops while the hart sits in
   WFI: an idle hang. One line fixes it:
   [`kernel/smp/0001-clocksource-esp32s31-systimer-tick-the-boot-CPU-only.patch`](../../kernel/smp/0001-clocksource-esp32s31-systimer-tick-the-boot-CPU-only.patch).
2. **Hart 1 has no tick.** It falls back to the RISC-V timer through SBI,
   and Espressif's OpenSBI has no timer device. GrieferPig gives each hart
   its own systimer comparator, interrupt matrix sources 33 and 34, routed
   to CLIC slot 41 of each hart (his `docs/en/hw-reference/interrupt-routing.md`).
3. **No IPIs.** Without an IPI driver, Linux falls back to SBI IPIs
   (`arch/riscv/kernel/sbi-ipi.c`), which fail as above. GrieferPig uses
   the chip's cross-core doorbell registers at 0x20586010 (to hart 0) and
   0x20586014 (to hart 1), matrix sources 65 and 66, routed to CLIC slot 40,
   behind Linux's `ipi_mux` (`drivers/irqchip/irq-esp32s31-smp.c`).
4. **No remote TLB or I-cache flushes.** Linux sends those as SBI remote
   fences when its IPIs are SBI's, so they fail too. With real Linux IPIs,
   Linux does them itself.
5. **The CLIC window is per hart.** 0x10A00000 shows the bank of the hart
   that reads it; the other hart's bank is at 0x10A10000 (GrieferPig,
   `CLIC_OTHER_HART_OFF` in `irq-esp-clic.c`). Espressif's driver maps only
   0x2000 bytes at 0x10A00000, so a mask or unmask that runs on hart 1
   changes hart 1's bank, while the device interrupt arrives at hart 0's.
   Threaded interrupt handlers unmask from a kernel thread that may run on
   either hart, so device interrupts could stay masked.
6. **Device interrupts stay on hart 0.** The interrupt matrix has one table
   per core (core 0's at 0x20585000, the one Espressif's device tree maps;
   core 1's 0x800 above it in GrieferPig's code). GrieferPig also keeps
   every device interrupt on hart 0.
7. **Spinlocks.** GrieferPig found that atomic memory operations (AMOs) and
   ordinary cached loads and stores do not see the same value of a lock word
   across the two harts, so the stock ticket lock (32-bit AMO to take, 16-bit
   store to release) leaves both harts spinning. He replaced it with an
   AMO-only lock, and routes `atomic_read_acquire()` and
   `atomic_set_release()` through AMOs (`arch/riscv/include/asm/spinlock.h`,
   `atomic.h`, commit bd15992). This is his finding, not checked here. Our
   one-hart system mixes AMOs and plain accesses all the time and works,
   so it is a two-hart effect. His patch covers the kernel only; whether
   musl's locks in user space are affected on two harts is an open question.
8. **Idle.** GrieferPig's harts poll in idle by default instead of
   sleeping in WFI. Real WFI needs `esp32s31_idle=wfi` and his OpenSBI,
   because "S31 does not reliably wake an M-mode WFI for an interrupt
   delegated to S-mode" (his `services.c`). Polling keeps both harts busy
   all the time, which costs power and heat.

Two things that do not need work:

- **Kernel in place from flash.** Upstream `head.S` already applies the XIP
  address fix-ups on the secondary entry path (`secondary_start_sbi`), and
  GrieferPig runs SMP with an XIP kernel.
- **Writing flash.** GrieferPig's OpenSBI parks the other hart in SRAM
  while the ROM writes flash, because a hart executing from flash would
  stall. Our kernel maps flash read-only (`CONFIG_MTD_ROM` with physmap),
  so this only matters if we ever write flash from Linux.

GrieferPig's kernel history is squashed (his SMP work sits inside "riscv:
port ESP32-S31 Linux support to 6.18" plus bd15992 and 87d6ed85), so there
is no clean SMP patch set to take. The pieces are
`drivers/irqchip/irq-esp32s31-smp.c` (327 lines) and changes to
`irq-esp-clic.c`, `irq-esp-intmtx.c`, `timer-esp32s31-systimer.c`,
`asm/spinlock.h`, `asm/atomic.h` and `kernel/irq/ipi-mux.c`.

## The ground rule

The plan says the boot stack (SPL, OpenSBI, U-Boot) stays as Espressif
ships it, and that kernel config changes and driver patches are allowed.
Per layer:

| Change | Rule |
| --- | --- |
| OpenSBI 5395e03 and U-Boot b2ec9ae | Still Espressif's code, but newer than what is on the board, and it changes the boot stack (including the CLIC fix on hart 0). To decide before section 4 of the guide. |
| `cpu@1` and `maxcpus=1` in the kernel's device tree | Kernel side, like the DMA pool move in step 20. |
| `CONFIG_SMP`, `CONFIG_NR_CPUS`, `CONFIG_HOTPLUG_CPU` | Config only. |
| The systimer patch, and later IPI, timer and CLIC drivers | Driver patches. |
| GrieferPig's OpenSBI (WFI guard, own timer) | Breaks the rule. Not needed if idle polls. |

## Next to the Wi-Fi plan

- **SRAM:** no conflict, with OpenSBI and U-Boot updated together (table
  above): OpenSBI still ends below 0x2F030000, where the radio's SRAM starts.
- **Device tree:** step 20 edits the DTB to move the DMA pool. The SMP
  guide adds `cpu@1` to that same edited source, so neither change undoes
  the other.
- **Kernel patches:** the systimer patch sits in `kernel/smp/`, apart from
  the Wi-Fi patches in `kernel/patches/`, and touches a different file than
  the DMA pool patch and the F-only FPU patch (`cpufeature.c`, `fpu.S`).
  The FPU patch saves F registers per task on a context switch, which also
  covers a task moving between harts (inferred).
- **The radio:** GrieferPig wrote his radio code on his SMP kernel. It
  keeps its interrupt path and main worker on hart 0 and uses hart 1 for
  receive work, falling back to hart 0 when hart 1 is offline (his
  `docs/en/api-reference/system/interrupts-smp.md`). So the one-hart port of
  step 21 is a case he supports, and turning SMP on later means testing the
  radio again with real concurrency.
- **Order:** the boot stack update also changes the CLIC set-up on hart 0
  (9edf48f), so Ethernet, USB and UART interrupts need a re-check after it.
  Doing it between Wi-Fi steps, not in the middle of one, keeps the two
  causes apart.

## The SIGILL problem

Freshly written code (pcre2's JIT) faults with SIGILL on the board; the
suspected cause is a stale instruction cache. How the I-cache is synced:

- The chip has one L1 data cache for both harts and one L1 instruction
  cache per hart, all in front of flash and PSRAM. That is how the ROM's
  cache map bits read (`CACHE_MAP_L1_ICACHE_0`, `_1`, `CACHE_MAP_L1_DCACHE`
  in Espressif's OpenSBI `rom.h`), and SPL enables exactly these three.
  `fence.i` does not reach them (Espressif's comment in `cacheflush.h`).
- One hart today: the `riscv_flush_icache` system call ends in
  `local_flush_icache_all()` (`flush_icache_mm()` is a macro for it without
  `CONFIG_SMP`), which does `fence.i` and Espressif's vendor SBI call 3:
  write back the whole D-cache and invalidate both I-caches.
- Two harts: `flush_icache_mm()` becomes the real function. It does the
  same local flush, which still invalidates both I-caches, then sends a
  remote `fence.i` to the other hart if it runs the same program, and
  marks the program's I-cache as stale everywhere else, so the next switch
  to it on another hart flushes again.

So SMP adds no new gap for the I-cache itself, since one vendor call
reaches both I-caches. It does add remote fences, which fail with
Espressif's OpenSBI until Linux has its own IPIs, more whole-cache flushes
on context switches, and a second hart whose timing changes when a stale
line is hit. The SIGILL cause should be found on one hart first.

## Options

1. **Wait for Espressif's kernel half.** The same Espressif developer wrote
   the OpenSBI and U-Boot halves, both dated 2026-08-18, and the kernel
   branch has nothing for SMP yet (`git ls-remote` on 2026-10-10:
   `integration/v6.18-esp32s31` is still dc0e382). That a kernel part follows
   is inferred.
2. **Port GrieferPig's kernel pieces** (items 2 to 8 above) onto Espressif's
   6.18, on Espressif's updated OpenSBI, with polling idle. Driver patches
   only, so within the rule once the boot stack is updated. Its size is
   comparable to the radio's interrupt glue in step 21 (estimated).
3. **Take GrieferPig's OpenSBI as well,** for real WFI in idle. Breaks the
   ground rule.

Recommended: run the experiment in the guide now, because it is small,
reversible, and shows on the board whether hart 1 starts. Leave the real
SMP for after Wi-Fi works, then take option 1 if Espressif has published
its kernel half by then, and option 2 if not.
